02 Problem Statement — The Crisis

₹1,200+ Crores in state and central scholarships go unclaimed or rejected every single year — not because students don't want them, but because navigating government portals feels like preparing for the civil services exam.

The Three Critical Roadblocks

🔀 Roadblock 1: Overlap & Rule Sprawl

Tamil Nadu alone runs 15+ welfare and scholarship schemes spanning Adi Dravidar & Tribal Welfare (SC/ST), BC/MBC/DNC Welfare, Pudhumai Penn, 7.5% Govt School Quota, Post-Matric Scholarships, AICTE Pragati/Saksham, Construction Workers Welfare Board, and Differently Abled Persons Welfare. Each has hyper-specific thresholds across community, income, gender, disability, schooling, degree, and first-generation status.

📄 Roadblock 2: Information Overload

A student cannot read 15 separate 40-page government gazette orders to know what they qualify for. There is no single unified source of truth that aggregates all scheme criteria in a digestible format.

⚠️ Roadblock 3: The "Conflict Trap" (The Biggest Problem)

Government rules strictly state: You cannot draw maintenance allowance from two overlapping state schemes simultaneously.

  • If a student applies to both, both get rejected for "double-dipping"
  • Or they pick a ₹4,000 scheme when they were legally entitled to a ₹40,000 bundle
A list of schemes is NOT a solution. Students need an optimal, legally valid decision engine.

05 The Secret Sauce — Conflict Engine & MWIS Algorithm

5.1 The Computer Science Problem

Matching overlapping, mutually exclusive schemes is a Maximum Weight Independent Set (MWIS) problem on a conflict graph.
Conflict Graph Model
  • Nodes = Eligible schemes (weighted by annual financial benefit in ₹)
  • Edges = Mutual exclusivity constraints (can't claim both)
  • Goal = Find the subset with maximum total weight and no two connected nodes

5.2 Two Conflict Mechanisms

Mechanism 1: exclusiveGroup

At most ONE scheme per group may be selected:

Group IDMeaningReal-World Basis
tn-fee-reimbursementSchemes paying/waiving same tuition feeNSP "One Student, One Scholarship"
tn-welfare-grantWelfare-board grants by parent statusCan't stack welfare grants
tn-merit-cashStandalone merit cash awardsOne merit award allowed
central-maintenance-allowanceCentral govt maintenance allowancesNSP dual-maintenance ban

Mechanism 2: conflictsWith

Explicit pairwise overrides for special cross-group conflicts using scheme IDs.

09 AI Integration — Philosophy & Constraints

🚫 Critical Architecture Principle: AI ≠ Decision Maker

The AI NEVER decides eligibility. It is used strictly for two tasks:

  1. Profile Extraction — parsing natural language into structured fields
  2. Explanation Phrasing — making deterministic results human-readable
Student Natural Language → AI Profile Parser (extraction only) ↓ Structured Profile {cat, edu, inc...} ↓ Deterministic Rule Engine (eligFn) ← NO AI HERE ↓ Match Results {eligible, bestCombo} ↓ AI Explanation Layer (phrasing only) → Human-Readable Summary

9.1 Profile Parser Service

  • Dual-mode: LLM extraction (primary) + regex/pattern-matching fallback (deterministic)
  • Handles all 28 Indian states + UTs with city name → state mapping
  • Recognizes TN-specific categories (BC, MBC, DNC — distinct from all-India OBC)
  • Income detection from NL: "1.5 LPA", "below 1 lakh", "₹2,50,000"
  • Parent occupation detection: government / construction / private
  • Missing field reporting — tells caller which required fields couldn't be extracted

9.2 AI Explanation Service

  • System prompt explicitly forbids adding/removing/changing any eligibility fact
  • 4-second timeout (not 15s) to prevent UI blocking
  • Template fallback produces identical factual content with less polished phrasing

9.3 Hallucination Prevention Guarantees

❌ AI Never Does✅ AI Only Does
See scheme rules or criteriaExtract what student actually stated
Output match/no-match decisionsRephrase what deterministic engine already decided
Invent amounts, deadlines, documentsStructure free text into validated enum fields
Guess missing informationReport missing fields back to caller

10 Data Ingestion Pipeline

An automated pipeline that keeps scheme data fresh by re-checking official government portals:

SOURCES Registry (hand-vetted official URLs) ↓ Fetch HTML (cheerio) / PDF (pdf-parse) ↓ Extract Text Content ↓ LLM Structuring (extraction-only prompt) ↓ Confidence Assessment ├── HIGH → Auto-apply to live Scheme doc │ (allowlisted fields only) │ Status: 'approved', reviewer: 'auto-ingestion' │ └── MEDIUM/LOW → Pending Proposal for human review endpoint ↓ SchemeChangeProposal (complete audit trail)

Safety Guarantees

Protected FieldWhy
eligFnEligibility rules always hand-authored by developers
amt / amtNumFinancial figures require human verification
verified / confidenceAudit integrity must be preserved

Discovery Mode

Crawls tn.gov.in/scheme_beneficiary_list.php for new schemes → filters to education/scholarship → generates proposals. Caps at 10 new candidates per run (politeness to source sites). Runs daily at 03:00 server time via node-cron.
